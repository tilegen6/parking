# ENTRY / EXIT Detection — натурные проверки

Цель: понять, **как камера определяет въезд и выезд**, и зафиксировать это для
backend (защита от дублей + расчёт длительности опираются на это).

Закрывает задачи Integration: 1, 2, 4, 5, 6, 7, 8, 9, 10.

## Что уже подтверждено (по реальному захвату)

Из дословного payload (`samples/real_capture_ipcamtalk.xml`, родственная модель,
прошивка V5.8.60) и проверки тулинга:

- ✅ Камера **присылает** `<direction>` в блоке `<ANPR>`: значения
  `forward` / `reverse`. Маппинг: `forward → ENTRY`, `reverse → EXIT`.
- ✅ Есть `<confidenceLevel>` (0..100) — годится для оценки качества ночь/день.
- ✅ Снимки приходят как отдельные multipart-части:
  `licensePlatePicture.jpg`, `vehiclePicture.jpg`, `detectionPicture.jpg`.
- ✅ `analyze.py` на живых дампах сам ответит, приходит ли direction
  (строка «Direction присылается камерой: ДА/НЕТ»).

⚠️ Это с **родственной** камеры. На нашей iDS-2CD7A46G0/P-IZHSY перепроверить —
прошивка/настройки могут отличаться (поле direction зависит от калибровки
«Vehicle Detection → Direction»).

## Гипотезы направления

1. **По полю `ANPR/direction`** — основной путь (подтверждён на родственной камере).
2. **По топологии** (запасной) — отдельные камеры/каналы на въезд и выезд,
   направление по `channelName` / `ipAddress`, если калибровка direction подведёт.

## Как снимать факты

```bash
# 1) поднять приёмник и навести камеру (httpHosts -> наш IP:8088)
python capture_server.py --port 8088 --out captures/
# 2) сделать проезды (день/ночь/медленно), затем свести
python analyze.py captures/ --dups-window 10
```
