## 1. Как это должно работать

### 1.1 Модель трека: три состояния вместо «мешка голосов»

```
PENDING ──(все ворота пройдены)──► DECIDED ──(трек закрылся)──► PASSED
   │
   ├──(decide_max_seconds истекли)──► GAVE_UP ──(трек закрылся)──► NO_PASS
   │
   └──(трек закрылся без решения)───────────────────────────────► NO_PASS
```

Ключевые инварианты:

1. **Сигнал «открыть» (`decision="open"`) эмитится только в `process()`, на живом кадре.** Ни `_collect_closed`, ни `flush` открыть шлагбаум не могут никогда — физически нет пути.
2. **Один трек = максимум один `open`.** Флаг `st.decided` сильнее любого кулдауна.
3. **Время считается в секундах монотонных часов** (`self._clock()`), а не в кадрах. Причина в коде: `StreamSource.frames()` (`sources.py:211-218`) делает `time.sleep(interval)`, затем `latest.take()`, и при отсутствии свежего кадра — `continue` без `yield`; при реконнекте (`sources.py:230-234`) кадров нет вовсе. Плюс инференс идёт в том же треде (`service.py:StreamManager._run`, строки 235-241), то есть реальный шаг = `interval` + 120-300 мс. «3 кадра подряд» — это не 0.6 с, а сколько получится.

### 1.2 Пошагово: машина подъезжает → шлагбаум открылся → машина проехала

**Шаг 0. Кадр приходит.** `StreamManager._run` (`service.py:237`) → `sp.process(frame)`. Фиксируем `now = self._clock()`.

**Шаг 1. Фильтр качества.** `frame_ok(frame.image, cfg.blur_threshold, cfg.dark_threshold)` — сейчас в потоке его нет. Кадр не прошёл → **всё равно** стареем треки (`tracker.update([], now)`) и идём в `_tick(now)`. Не стареть на плохом кадре нельзя: ночью в дождь половина кадров смазана, треки станут бессмертными и две машины сольются.

**Шаг 2. Детекция + OCR всех номеров кадра.** `Pipeline.process_frame_multi(image) -> list[FrameResult]` — по одному лучшему чтению на каждый регион детектора. Сегодня `process_frame` схлопывает кадр до одного кандидата, и вся геометрия ниже считалась бы по боксу, прыгающему между машинами.

**Шаг 3. Трекинг.** `tracker.update([r.box for r in results], now)` — все боксы кадра. Ассоциация IoU; для трека, который уже терял бокс (`age > 0`), порог переподхвата мягче (`reacquire_iou=0.1` вместо `0.3`) — иначе машина за секунду уезжает из своего старого бокса и рождается дубль-трек.

**Шаг 4. Накопление голоса.** По каждому треку: `st.vote.add(plate, conf, weight, ts=now)`. Вес чтения — не единица (см. §3.1): чем крупнее и резче кроп, тем больше вес. Окно голосования — `vote_window_seconds=3.0` (сейчас поле мёртвое): чтения старше окна выпадают. Для машины, стоящей 40 секунд, это принципиально — иначе голос за первое чтение с 20 метров весит столько же, сколько за последнее с 4 метров.

Одновременно обновляется геометрия трека: `first_area`, `area_max`, `area_hist` (deque на `leave_window=4`), `last_box`, `last_hit=now`, `ever_grew`, `in_zone`.

**Шаг 5. Ворота решения (`ready_to_decide`) — на каждом кадре, по всем PENDING-трекам.** Порядок от дешёвых к дорогим, каждое возвращает **причину отказа строкой** — она уходит в `/stream/status`:

| # | Ворота | Причина отказа | Зачем |
|---|---|---|---|
| 1 | `not st.decided and not st.gave_up` | — | один трек = одно решение |
| 2 | `now - st.last_hit <= decide_freshness_seconds` (0.7 с) | `stale_hit` | **главный предохранитель против «открыли вслед»**: номер должен быть в кадре прямо сейчас |
| 3 | `st.last_box is not None` | `no_box` | fail closed: `WholeFrameDetector` (`detect.py:37-39`) отдаёт `Region(frame, None)`, `stream.py:75` подставляет весь кадр — тогда все размерные и ростовые проверки вырождаются. Детектор выбирается в Студии отдельной выпадашкой, комбинация `whole` + шлагбаум реальна |
| 4 | `st.hits >= min_hits` и `vr.votes >= decide_min_votes` (3) | `few_votes` | сегодня проверяется только `hits` |
| 5 | `vr.votes/vr.total >= decide_agree_ratio` (0.6) **и** `vr.votes - vr.runner_up >= decide_vote_margin` (2) | `no_agreement` | доля ловит «1 из 5», отрыв ловит мигание A/B/A/B, которое доля пропускает |
| 6 | `vr.confidence >= decide_confidence` (0.85) **и** `normalize_plate(vr.plate).is_valid` | `low_conf` / `bad_format` | 0.85 = backend `recognition_min_confidence` — закрывает CV-1 без правок бэкенда |
| 7 | Геометрия: якорь `bottom_center` бокса внутри ROI (если задан), `h_box/h_frame` в `[min_plate_height_ratio, max_plate_height_ratio]`, `st.ever_grew` (площадь хоть раз выросла в `growth_ratio=1.15` раз от первой), **и НЕ** `area_hist[-1] < leave_shrink_ratio * area_max` | `out_of_roi` / `box_too_small` / `never_grew` / `leaving` | см. §1.3 |

**Шаг 6. Решение.** Все ворота пройдены → `_decide(st, vr, now)`:
- проверка реестра решений `self._decisions[plate]` (adopt, см. §1.5);
- собирается `FrameResult` из победителя голосования, вызывается `pipeline._emit(voted, st.last_frame, self.sinks, decision="open")`;
- **ровно один POST** на `/api/v1/hikvision/anpr-event`;
- `st.decided = True`, `st.decision_plate = vr.plate`;
- в реестр пишется `hold` по фактическому вердикту бэкенда из `rec["backend_response"]["session_action"]` (`pipeline.py:198` кладёт его синхронно).

**Шаг 7. Машина стоит перед стрелой / проезжает.** Трек живёт, `decided=True` → **ноль запросов**. Сейчас в этом месте backend вынужден разгребать дубли на своей стороне (`session.py:_apply_duplicate_entry`).

**Шаг 8. Трек закрылся** (не в `tracker.active` **или** `now - st.last_hit > lost_timeout_seconds`):
- был `DECIDED` и финальный голос совпал → **ничего не шлём**, счётчик `passed`;
- был `DECIDED`, но финальный голос разошёлся → **второй POST не шлём** (см. «что не берём», §2.6), пишем локальную запись `kind="correction"` в ленту `/stream/events` и в лог — это сигнал на калибровку, а не команда;
- решения не было, но трек **правдоподобный** (был в ROI / прошёл размер, `hits >= min_hits`, голос есть, `conf >= confidence_threshold`) → POST с `decision="observe"`: учётный след в БД остаётся, стрела не трогается. На камере ВЫЕЗДА это критично: `session._handle_exit` достижим только из события, иначе сессия не закроется никогда;
- трек «мусорный» (ни разу не в зоне / бокс всегда мельче порога) → **никакого POST**, только локальная запись `kind="zone_miss"` и счётчик. Это и есть отсев «миллиона запросов» от фона.

**Шаг 9. Повторный подъезд.** Реестр решений хранит `plate → (at, hold, track_id)`. `hold` **зависит от того, что ответил бэкенд**:
- `session_action ∈ {created, entry_restarted, closed, updated_last_seen, duplicate_exit}` (все реально возвращаются из `session.py:408, 455, 462, 481, 560`) → `rearm_seconds = 25 с`;
- любое другое значение, включая `low_confidence`, `access_denied_red`, `exit_denied_unpaid`, `event_without_session`, `ignored`, **а также отсутствие ответа** (`backend_error` в `pipeline.py:200`) → `rearm_denied_seconds = 5 с`.

Смысл: длинный hold ставим только тогда, когда точно знаем, что бэкенд отработал. Машину не пустили, водитель сдал назад и подъехал заново через 20 с — система реагирует, а не молчит 40 с. Сегодняшний плоский `cooldown_seconds=60` воспроизводит ровно жалобу «тупит».

### 1.3 Как не открыть уехавшей / чужой машине

| Сценарий | Что его гасит | Почему именно так |
|---|---|---|
| Машина уже уезжает | Ворота 2 (`stale_hit`, 0.7 с) + `leaving` по `area_hist[-1] < 0.8·area_max` + отсутствие пути эмиссии из `_collect_closed` | Сравнение с **максимумом**, а не с первым кадром: трек, родившийся далеко, может дать `last/first > 1.15` уже на отъезде — проверка «вырос относительно первого» этот случай пропускает |
| Машина по соседней полосе / встречка | ROI (якорь `bottom_center` — нижняя середина бокса, ближайшая к полотну) + `min_plate_height_ratio` | Бокс с соседней полосы, налезший краем на зону, отсекается якорем; дальний номер — размером. Установочный регламент требует «одна камера — одна полоса», ROI это дублирует |
| Номер на плакате / отражение / припаркованная в фоне | `ever_grew` (входной гейт: трек обязан хоть раз вырасти) | Статичный объект голосует идеально и стабильно вечно — по одним только голосам система бы его открыла. Это дыра дефолта «ROI = весь кадр», её затыкает именно `ever_grew` |
| Машина подъехала и **встала** | `ever_grew` уже взведён на подъезде; далее площадь может не расти — это не мешает | Жёсткое `area_last/area_first >= 1.15` на каждом кадре убило бы самый частый сценарий у стрелы. Формула: **вырос — допускает, стоит — не мешает, уменьшается — запрещает** |
| Неверно прочитанный номер | Ворота 5 (доля + отрыв) и 6 (0.85 + формат KZ) | Решение по 3-5 чтениям вместо 12-15 — статистики меньше, компенсируем согласованностью, а не длиной трека |
| Очередь из двух машин | `process_frame_multi` + мультибокс в трекер | Без этого голоса чужой машины попадают в чужой `MajorityVote` — самый скрытый источник «открыли не тому» в текущем коде |
| Плохой кадр (смаз/тьма) | `frame_ok` в начале `process()` + вес голоса по резкости кропа | При решении по 3 чтениям вес одного мусорного чтения втрое выше, чем раньше |

### 1.4 Неуверенное чтение — три коридора, а не один порог

| Условие | Что делаем |
|---|---|
| `conf >= decide_confidence` (0.85) **и** все ворота | `decision="open"` — POST, сигнал шлагбауму |
| `confidence_threshold` (0.5) `<= conf < 0.85`, либо ворота не сложились, но трек правдоподобный | `decision="observe"` на закрытии трека — POST, попадает в БД и на дашборд; backend режет его в `_is_low_confidence` (`session.py:124`) и сессию не создаёт |
| `conf < confidence_threshold` или трек мусорный | ничего не шлём, локальная запись + счётчик |
| `gave_up` (за `decide_max_seconds` стабильность не набралась) | `observe` с `flag`, счётчик `stalled`, **алерт оператору**. Это обязательный запасной путь: без кнопки ручного открытия систему в бой выпускать нельзя |

### 1.5 Анти-спам: гарантии по числу POST

1. **Флаг на треке.** Нормальный проезд = **ровно 1 POST**. Не «обычно один», а структурно один: `open` эмитится с ребра PENDING→DECIDED, повторные кадры до этой ветки не доходят.
2. **Мусорные треки не шлют ничего.** Фон парковки, соседняя полоса, номер на плакате — 0 POST. Сегодня каждый такой трек даёт полноценное событие и открывает сессию.
3. **Два раздельных кулдауна.** `_decisions` (открытие, hold 5/25 с по вердикту) и `_cd_log` (учёт, `cooldown_seconds=60`). **Учётное событие никогда не ставит hold на открытие** — сегодня один общий словарь означал бы, что низкоуверенное наблюдение на минуту глушит легитимный сигнал.
4. **`gave_up`.** Машина с грязным номером, стоящая 5 минут, не крутит проверку 1500 раз и не шлёт ничего.
5. **Adopt при перерождении трека.** Трек развалился (`max_age`) и родился заново с тем же номером в пределах hold → второй POST не уходит, новый трек сразу помечается `DECIDED` с `adopted_from`. Без adopt он закрылся бы как «не проехал» по машине, которую только что пустили.
6. **`_gc_decisions(now)`.** Сегодня `self._cooldown` (`stream.py:56`) растёт бесконечно — ключи не удаляются никогда, на боевом потоке это тысячи записей за сутки.

### 1.6 Тайминг: честная арифметика (без розовых цифр)

Реальный шаг кадра = `1/video_fps` + инференс (fastplate + open-image-models на CPU в Docker: 120-300 мс), потому что POST и инференс идут в том же треде, что и чтение (`service.py:235-241`).

- `video_fps=10` → шаг ≈ 0.22-0.4 с.
- `decide_min_votes=3` → решение через **0.7-1.2 с** после первого распознавания.
- Скорость подъезда 5-10 км/ч = 1.4-2.8 м/с → пройдено 1-3 м.
- При геометрии из установочного регламента (номер читается с 8 до 4 м до стрелы) решение принимается **за 3-6 м до стрелы**.
- Против нынешнего «`max_age` кадров после ухода номера из кадра» — выигрыш порядка **2.5-4 с**.

Отдельно: `sink.py:BackendSink.send` (`sink.py:67`) — `httpx.post(..., timeout=15)` синхронно внутри цикла кадров. Один залипший бэкенд = до 15 с полной слепоты, следующая машина теряется целиком, и весь выигрыш по времени обнуляется. Таймаут вниз до 3 с + вынос отправки в очередь с рабочим тредом (этап D).

### 2.2 `cv/recognizer/vote.py`

Полноценный enum фаз с `STANDING`/`LEAVING` как отдельными состояниями не заводим: `leaving` — это **вето внутри ворот**, а не состояние; состояний реально три (§1.1).

| 7 | **Снап к белому списку** | `access_entry` в бэкенде уже есть. Строго: расстояние Левенштейна 1, единственный кандидат в списке на этом расстоянии, факт снапа логируется отдельным полем. Иначе начнёт «чинить» чужие номера в номера жильцов — самая дорогая ошибка |

## 4. Чек-лист установки и приёмки на объекте

Всё измеряется **на том потоке, который реально идёт в CV**, а не в веб-превью камеры — превью показывает субпоток и врёт.

### 4.1 Блокеры (без них дальше идти бессмысленно)

- [ ] **Поток переключён с субпотока 102 на 103 (1920×1080, 12-15 fps, H.264 High, CBR 6-8 Mbps, GOP = FPS).** Субпоток 640×480 при f=4 мм и D=5 м даёт ~46 px на плашку — это физически нечитаемо никаким OCR и **не лечится кодом**. Менять `Camera.stream_path` на `/Streaming/Channels/103`. Не 101 (4K): `StreamSource` декодирует все кадры, 4K съест CPU без пользы.
- [ ] **Ширина плашки на кадре ≥ 133 px, целевое 167-250 px.** Замер: машина в точке остановки, `ffmpeg -rtsp_transport tcp -i rtsp://.../103 -frames:v 1 shot.png`, измерить в редакторе.
- [ ] **Выдержка ручная: день 1/1000, ночь 1/500.** Два профиля Day/Night. Медленнее 1/250 — никогда: на 10 км/ч смаз 4-8 px стирает символ. `Max Gain` ≤ 50-60.
- [ ] **Ночной проезд с фарами в камеру:** плашка читается, вокруг фар нет расплыва (HLC ON ночью, level 50; WDR ON только днём).
- [ ] **Glass-to-glass задержка ≤ 500 мс** (секундомер перед камерой vs картинка). Больше — CV будет открывать уезжающей машине независимо от логики.
- [ ] **Контрольный прогон 30 проездов** (10 день / 10 сумерки / 10 ночь) с журналом «что ожидали / что произошло / за сколько секунд».

### 4.2 Геометрия

- [ ] Камера на отдельной стойке, **не на стреле** (вибрация = смаз и ложные треки).
- [ ] Высота объектива 1.2-1.8 м, смещение от оси полосы 0.5-1.5 м (иначе фары и зеркальный блик ретроотражающей плашки в лоб).
- [ ] Углы: вертикальный ≤ 20° (макс 30°), горизонтальный ≤ 20° (макс 30°), крен ≤ 2° (макс 5°) — deskew в пайплайне нет, крен бьёт по OCR напрямую.
- [ ] Зона уверенного чтения ≥ 4 м, ориентировочно от 8 до 4 м до стрелы. Стрела **вне кадра** в обоих положениях.
- [ ] Одна камера — одна полоса. Въезд и выезд — две камеры.
- [ ] ИК: Smart IR ON, режим Manual, яркость 30-50 % (на 100 % плашка выбеливается в белый прямоугольник). Проверить купол на внутреннюю засветку ночью без машины.
- [ ] PAL 50 Hz, NTP UTC+5, `rtsp_transport=tcp`, `CAP_PROP_BUFFERSIZE=1`.
- [ ] Козырёк, термокожух (паспортные −30 °C — это порог работы, а не холодного старта), PoE + грозозащита, регламент протирки стекла.

### 4.3 Настройка логики шлагбаума (после того, как оптика принята)

- [ ] `CV_FPS=10` на шлагбаумной камере.
- [ ] Подогнать машину к стоп-линии, снять `last_height_ratio` из `/stream/status`, поставить `min_plate_height_ratio ≈ 0.7 × замер`.
- [ ] Нарисовать ROI по своей полосе, проверить по превью (зона отрисовывается), убедиться, что соседняя полоса вне.
- [ ] Прогнать 10 подъездов: `decided > 0`, `zone_miss` только по чужим машинам, `reason` у неудачных треков осмыслен.
- [ ] Прогнать 5 **отъездов** (машина сдаёт назад / уезжает): `open` не приходит ни разу.
- [ ] Прогнать проезд по соседней полосе: `open` не приходит.
- [ ] **Кнопка ручного открытия в админке работает** и алерт по `gave_up` настроен. Без запасного пути `gate_mode` в бой выпускать нельзя: грязный номер в дождь = стрела не поднимется вообще, и это хуже текущего поведения.
- [ ] Час непрерывной записи потока: 0 разрывов, потери пакетов 0; фактический шаг кадра совпадает с ожидаемым.
- [ ] Проверить, что `barrier.py` действительно подключён (на момент написания — 0 байт). Иначе приёмка «шлагбаум открылся» невыполнима физически.

## 5. Метрики

Единица измерения — **проезд**, не кадр и не событие. Все с разбивкой по камере, времени суток (4 корзины) и погоде: средняя «95 %» скрывает «ночью 60 %».

### 5.1 Бизнес-метрики (то, что показываем заказчику)

| Метрика | Как считаем | Цель |
|---|---|---|
| Доля успешных автопроездов | шлагбаум открылся сам по верному номеру / все проезды | ≥ 95 % день, ≥ 90 % ночь |
| **Время до решения, p50/p95** | от первого кадра трека с номером до POST | **p95 ≤ 1.5-2 с**. Мерить **до** переделки — иначе улучшение нечем доказать |
| Ложные открытия (FP) | открытий по номеру, которого не было / чужому | **0** для зелёного и красного списков; ≤ 1 на 1000 для платных |
| Ложные неоткрытия (FN) | проезды, потребовавшие второго подъезда или ручного открытия | ≤ 5 % |
| Доля ручных вмешательств | (события с флагом + ручные открытия) / проезды | ≤ 5 %, тренд вниз по неделям. **Главный прокси FN, разметки не требует** |

### 5.2 Технические (в `/stream/status`, снимаются без разметки)

| Метрика | Источник | О чём говорит |
|---|---|---|
| `events_per_pass` | `decided` vs число закрытых треков | должно быть ровно 1. Дубли и нули видны сразу |
| `decided / passed / no_pass / zone_miss / stalled / suppressed` | счётчики `StreamPipeline` | здоровье логики решения |
| Распределение `last_block_reason` | по живым и закрытым трекам | **самая полезная строка при разборе «почему не открылось»**: `out_of_roi` = камера/зона, `low_conf` = оптика/ночь, `no_agreement` = OCR, `stale_hit` = задержка потока |
| `agreement = votes/total` по событиям | `VoteResult` | медиана здоровой системы > 0.8. Просадка = грязь на стекле, расфокус, ночной режим |
| Доля `is_valid=False` среди событий | `flag` | растёт → сломался кроп / фокус / ракурс |
| Доля кадров, отсеянных `frame_ok` | новый счётчик | ночью > 30 % → проблема в свете/выдержке, а не в порогах. **Пороги крутить только после приёмки оптики** |
| Потерянные отправки | `backend_error` в `pipeline.py:200` | сейчас 0 не гарантирован: при ошибке отправки событие теряется, а `events_emitted` считает его отправленным |
| Latency OCR p50/p95, фактический шаг кадра | `metrics.py` + `/stream/status` | если шаг вырос до 0.5 с — выигрыш по времени съеден инференсом |
| Uptime потока | доля минут с живыми кадрами | сейчас не измеряется: `camera.last_seen_at` обновляется **только событием** (`recognition._mark_camera_alive`) → ночью без машин камера числится «оффлайн» |
| Расстояние Левенштейна от события до ближайшего номера из белого списка | `metrics.levenshtein` + `access_entry` | доля событий с расстоянием 1-2 — почти наверняка ошибки OCR по известным машинам. **Бесплатный детектор деградации без всякой разметки** |

### 5.3 Офлайн (после сбора датасета)

- per-frame exact / char accuracy / detection rate — уже есть в `evaluate.py:132-135`;
- **per-track (per-event) exact** — главное, чего нет: доля проездов, давших ровно одно событие с верным номером. Это и есть метрика, которую видит заказчик;
- precision / recall / FAR как функция порога, отдельно по каждому движку и по `is_valid`;
- confusion-матрица символов → правки `normalize.LETTER_TO_DIGIT`;
- разбивка метрик по высоте кропа, резкости и времени суток — отвечает на «с какой дистанции камера реально читает» и задаёт `min_plate_height_px`.

Плюс дешёвая ручная сверка: писать на диск кропы для 1-2 % событий вместе с предсказанием и составом голосования, раз в неделю сверять 100 штук глазами. Это даёт настоящий exact на проде за 20 минут работы; без этого все онлайн-метрики остаются прокси.
