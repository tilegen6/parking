# Технологические решения и ADR

Состояние решений: предлагается сохранить реализованный стек для первой предзащиты, проверить ограничения и согласовать с руководителем. Ниже — три ключевых решения по три альтернативы. Оценки сложности/переноса — инженерное суждение по существующему коду, а не измерение быстродействия.

## ADR-01: серверная платформа

Критерии: валидация входных событий (FR-01), API-документация (NFR-08), интеграция Python/CV, стоимость переноса текущих модулей.

| Альтернатива | Сильная сторона по источнику | Цена/ограничение в этом проекте | Решение |
|---|---|---|---|
| [FastAPI](https://fastapi.tiangolo.com/features/) [S11] | Типы Python, Pydantic, OpenAPI, ASGI | Нужно самостоятельно контролировать транзакции и фоновые операции | Выбрано: уже есть роутеры и тесты; CPU-CV вынесен из API |
| [Django REST Framework](https://www.django-rest-framework.org/) | Сериализация, permissions, browsable API и экосистема Django | Переход потребует переноса текущих моделей/миграций; административные удобства не оправдывают его сейчас | Резерв для проекта, где основная работа — CRUD/администрирование |
| [NestJS](https://docs.nestjs.com/) | Модульная серверная архитектура TypeScript | CV всё равно остаётся Python-сервисом; backend придётся переписать | Разумная альтернатива TS-команде, отклонена для текущего MVP |

Следствие: FastAPI не выполняет тяжёлое распознавание в обработчике бизнес-API. Интерфейс CV — отдельный HTTP-контракт. Проверка — schema/API-тесты и нагрузочный тест NFR-02. Пересмотр: если требования/команда меняются либо измерения выявят неподходящий профиль нагрузки.

## ADR-02: основное хранилище

Критерии: уникальная активная сессия FR-02, согласованная оплата FR-06, связи камера–событие–сессия–платёж, миграции и восстановление.

| Альтернатива | Возможности | Цена/ограничение | Решение |
|---|---|---|---|
| PostgreSQL 16 | [Транзакции](https://www.postgresql.org/docs/16/tutorial-transactions.html), [ограничения](https://www.postgresql.org/docs/16/ddl-constraints.html) [S12] | Требует миграций, резервирования и проверки конкуренции | Выбрано: соответствует текущему SQLAlchemy/Alembic и связанной модели |
| MySQL/InnoDB | [Транзакции, блокировки и MVCC](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-model.html) | Проверить замену PostgreSQL-специфичных ограничений и миграций | Подходит концептуально; переход не даёт подтверждённой выгоды |
| MongoDB | [Многодокументные транзакции](https://www.mongodb.com/docs/manual/core/transactions/) | Документная модель возможна, но требует другого проектирования связей и инвариантов | Не выбрана для транзакционного ядра; не заявляется, что транзакций в MongoDB нет |

Следствие: снимки хранятся отдельно в MinIO; БД содержит ссылки и операционные данные. Redis не является источником истины для оплаты/сессии. SQLite в тестах ускоряет проверки, но не заменяет PostgreSQL-тест ограничений и конкурентных транзакций. Пересмотр — после измерений либо изменения модели данных, а не из-за общей популярности технологии.

## ADR-03: обмен между камерой/CV и backend

Критерии: минимальная сложность пилота, задержка, повторная доставка, аудит потерь и повторов (FR-01/02/12, NFR-03).

| Альтернатива | Гарантии и преимущества | Ограничение | Решение |
|---|---|---|---|
| HTTP JSON/multipart | [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html): явные запрос/ответ, совместимость с существующим приёмником камеры | POST сам по себе не exactly-once; таймаут после commit неоднозначен; нужен договор повтора и дедупликация | Выбрано для MVP: фактические пути уже реализованы |
| RabbitMQ + подтверждения | [Consumer acknowledgements/publisher confirms](https://www.rabbitmq.com/docs/confirms) [S13] позволяют строить подтверждаемую доставку | Нужны брокер, долговечность, outbox/consumer dedup и эксплуатация; дубликаты всё равно возможны | Вариант следующего этапа при подтверждённых потерях/нагрузке |
| Локальный дисковый spool + HTTP replay | [Исходные capture/replay инструменты](../../cv/replay.py) позволяют повторить сохранённое событие и расследовать проблему | Прототип инструментов не является автоматическим durable delivery; нужны квоты, подтверждения и безопасный replay | Контролируемый стендовый fallback; автоматизация FR-12 остаётся работой |

Следствие: текущий JSON CV→backend преобразуется в совместимый Hikvision-style payload; отдельный endpoint «универсального события» не объявляется существующим. Ошибку доставки нужно показать оператору/в журнале, а не тихо трактовать как успешно созданную сессию. Надёжная очередь не включается только потому, что Redis присутствует в Compose. Пересмотр — при наличии измеренной потребности в офлайн-накоплении или нескольких независимых потребителях.

## Связанные решения

OCR остаётся заменяемым адаптером: готовый plate OCR, EasyOCR и детерминированный template-движок имеют разные назначения. Template служит тестовым контролем; его результаты на собственном шрифте не являются доказательством качества реального OCR. Собственное обучение требует разрешённых данных, отдельного облачного эксперимента и сравнения, а не изменения авторских метаданных модели.
