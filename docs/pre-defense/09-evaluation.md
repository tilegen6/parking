## Данные и этика измерения

До сбора подтвердить разрешение клиента, допустимость хранения, сроки удаления и доступ. Рабочие изображения и журналы с номерами хранить вне Git, в согласованном закрытом месте. В Git — описание схемы, обезличенные агрегаты, hash manifest без номеров/фото. Не обещать юридическое соответствие без отдельной проверки применимых требований.

Тестовый набор: минимум 300 независимых проездов, не меньше 20 автомобилей при возможности; ≥75 дневных, ≥75 ночных, ≥30 с наклоном/частичным закрытием/плохим качеством (страты могут пересекаться). Соседние кадры одного проезда не независимые наблюдения. Разделять train/validation/test по автомобилю и дню; правила/пороги подбирать только на train/validation, затем заморозить. Если собственного обучения нет, всё равно отделить подбор порога от финального теста. Два разметчика проверяют строку и границы номера, разногласия разбираются до измерения. Реальные данные сейчас не собраны этой работой.

## Baseline и метрики

B0 — тот же фиксированный детектор+готовый OCR, один кадр, без KZ-коррекции и временного vote. B1 — B0 + KZ-нормализация. B2 — B1 + временная агрегация на тех же проездах. Это абляция проекта; не сравнивать разные наборы и не выбирать для B2 лучшие кадры вручную. Движок/веса, параметры, commit и seed фиксируются в manifest. Дополнительно можно сравнить on-device Hikvision при доступе к тому же проезду; такой результат пока отсутствует.

Exact-match = число проездов с полностью верно распознанным номером / все размеченные проезды. CER = суммарное редакционное расстояние / число символов эталона. Detection recall@IoU≥0.5 считается отдельно, когда есть bbox-разметка. Coverage = автоматически принятые / все проезды. False accept = неверно принятые / все автоматически принятые; отказ не прячется в знаменателе точности. Дубли/потери считаются на уровне логического проезда, а не обработанного кадра.

Для долей публиковать 95% Wilson interval и размер выборки; для разности B0/B1/B2 — парный bootstrap по проездам с фиксированным seed и 1000 повторов. Если данных недостаточно для уверенного вывода, сообщить неопределённость. Успех пилота требует согласованных целей NFR-01 и отсутствия роста опасных false accept; высокий exact-match при агрессивном исправлении не считается достаточным.

## Нагрузка, отказы и воспроизводимость

Предложенный reference для CV — **облачный** разрешённый стенд 4 vCPU/8 GB без GPU, 1280×720, два потока с выборкой 5 fps; 30 s warm-up, затем ≥10 min, cold-start отдельно. Это измерительная конфигурация, а не утверждение достаточной мощности. Если очередь растёт, фиксировать backlog и пропуски. Для API — 5 requests/s 10 min на синтетических данных с отдельными БД/объектным хранилищем; сохранять сырые timings без секретов, p50/p95/p99 и error rate. При смене оборудования сравнение повторяется.

Fault matrix: отключить камеру, API, сеть до/после commit, платёжный callback, MinIO; повторить ENTRY и callback; перезапустить контейнер. Никаких команд на реальный барьер и денежных операций без отдельного согласованного испытания. Локальные ML-модели и inference-серверы в этой подготовке не устанавливаются. Unit-тесты используют синтетику и подмены.

Протокол каждого прогона: фактическая дата, git SHA, команда, окружение/версии, manifest данных, параметры, ожидаемое поведение, сырые результаты, итог по каждой метрике, ошибки/ограничения, ссылка на исправление. Не заполняйте измерения запланированными значениями.
