# CV: распознавание потока с обычной камеры (RTSP/телефон)

Дата: 2026-07-13 · Статус: утверждён · Ветки: `cv` (ядро), `frontend` (панель)

## Задача

Дать системе распознавать номера из **живого видеопотока обычной IP-камеры**
(не Hikvision-ANPR, которая сама шлёт события). Ключевое требование —
**не спамить событием «въезд», пока машина едет через кадр**: один проезд =
ровно одно событие. Плюс подготовить «слот» под быстрое подключение реальной
камеры и дать проверить механику **сейчас** телефоном-как-IP-камерой.

## Что уже есть (own-cv-v1, в main)

- `Pipeline.process_frame` — детект номера + OCR одного кадра.
- `Pipeline.run_video` — покадрово: `SimpleTracker` (IoU, один объект = один
  трек) + `MajorityVote` по треку → **одно событие на трек**. Но эмиссия
  **батчевая**, в конце файла — для бесконечного потока не годится.
- `SimpleTracker`, `MajorityVote`, фильтр качества кадра (`frame_ok`).
- `BackendSink` → `POST /api/v1/hikvision/anpr-event` (тот же приём, что у камеры).
- `direction` — из конфига (топология: камера въезда / выезда).
- Бэкенд сам дедупит (`updated_last_seen` / `duplicate_exit`).

## Чего не хватает (объём работы)

1. **Источник живого потока** (RTSP/MJPEG/файл) с переподключением.
2. **Онлайн-эмиссия**: событие при *закрытии* трека, а не в конце файла.
3. **Воркер + эндпоинты** управления потоком в CV-сервисе.
4. **Панель в Студии** для запуска/наблюдения.
5. **Тест**, доказывающий «один проезд = одно событие».

## Решения (утверждены)

- **Вход теста**: телефон как IP-камера (`http://<phone-ip>:8080/video` или
  `rtsp://…`). `cv2.VideoCapture(url)` открывает и это, и боевой RTSP — **один
  код**. «Слот под камеру» = поле URL (вставил — работает).
- **Управление**: панель в Студии, вкладка «Тест CV».
- **Направление**: топология — направление задаётся на поток (entry/exit).
  Для теста одним телефоном: ставим entry, затем переключаем на exit.
- **Эмиссия (подход A)**: событие на **закрытии трека** (машина ушла из кадра:
  трек состарился на `max_age` кадров) при `hits ≥ min_hits` и валидном
  majority-vote, с **кулдауном по номеру** (по умолчанию 60с) против повторов.

## Архитектура и компоненты

Каждый компонент — одна ответственность, тестируется отдельно.

### 1. `StreamSource` (`cv/recognizer/sources.py`)
Оборачивает `cv2.VideoCapture(target)`; `target` = `rtsp://…`, `http://…/video`,
индекс вебки или путь к видеофайлу (для оффлайн-демо). `frames()` отдаёт `Frame`
с реальными таймстампами, прореженные до `target_fps` (~5). Переподключение с
бэкоффом при разрыве; останавливается по флагу `stop()`. Ничего не знает о
распознавании. Тест — с фейковым `VideoCapture`.

### 2. `StreamPipeline` (`cv/recognizer/stream.py`) — сердце анти-спама
Онлайн-аналог `run_video`. На каждом кадре: `process_frame` → `tracker.update` →
per-track `MajorityVote`. Хранит по треку: hits, vote, последний бокс, лучший
кадр. **На закрытии трека** (был активен, стал неактивен) решает эмитить:
`hits ≥ min_hits` И vote даёт валидный/уверенный номер И номер не в кулдауне →
`RecognitionEvent(direction=cfg.direction)` в синки; ставит `cooldown[plate]=now`.
Чистая логика над кадрами — тест синтетикой со стаб-детектором/OCR.

Параметры (в `RecognizerConfig`): `min_hits` (напр. 3), `cooldown_seconds` (60).

### 3. `StreamManager` + эндпоинты (`cv/service.py`)
Менеджер держит воркер-потоки по `camera_name` (thread-safe статус/события/превью).
Эндпоинты:
- `POST /stream/start {url, direction, camera_name?, version?}` — старт воркера
  (StreamSource → StreamPipeline → BackendSink). Идемпотентно на камеру.
- `POST /stream/stop {camera_name?}` — стоп + join.
- `GET /stream/status` — running, url, direction, fps, кадров, последний номер,
  счётчики событий, реконнект/ошибка.
- `GET /stream/events?since=` — кольцевой буфер последних событий (для лога UI).
- `GET /stream/preview` — последний размеченный кадр (JPEG/data-url).

Воркер — обычный поток на блокирующем `cv2.read()` (uvicorn не блокируется).

### 4. Панель Студии (`frontend`, вкладка «Тест CV»)
«Живой поток (камера)»: поле URL (плейсхолдеры: телефон + rtsp), выбор
направления Въезд/Выезд, имя камеры, версия; Старт/Стоп. Живьём: статус
(fps, кадры, реконнект), **последний размеченный кадр** (поллинг ~1с), лента
событий (номер · направление · conf · ответ бэка). Хуки в `api/hooks.ts` → CV
(`VITE_CV_URL`). Одно-фото тестер остаётся рядом.

## Поток данных

Камера/телефон → `VideoCapture` → `StreamSource` (~5fps) → `StreamPipeline`
(детект+OCR+трек+vote) → **закрытие трека** → `RecognitionEvent(direction)` →
`POST /anpr-event` → бэкенд (создание/закрытие сессии + дедуп) → видно в
«Сейчас на парковке»/Сессиях. Параллельно событие+кадр → в память CV → панель
поллит `/stream/events` и `/stream/preview`.

## Обработка ошибок

- Поток не открылся/оборвался → реконнект с бэкоффом; статус «reconnecting» +
  последняя ошибка; UI показывает.
- Ошибка POST в бэкенд → событие логируется с `backend_error`, воркер живёт.
- Плохие кадры (смаз/темно) → отсекает `frame_ok`.
- Жизненный цикл: старт идемпотентен на камеру; стоп с join-таймаутом; на
  shutdown сервиса — стоп всех.
- Ресурсы: fps ~5, один воркер на камеру, ограниченное кольцо событий и один
  кадр превью (без роста памяти).

## Тестирование

**pytest (детерминированно, оффлайн)** — `cv/tests/test_stream_emission.py`:
- одна «машина» ~15 кадров и уходит → **ровно 1 событие** на закрытии, номер по
  голосованию, верное направление;
- две машины → 2 события;
- мигание номера в пределах трека → всё ещё 1;
- тот же номер после кулдауна → 2; внутри кулдауна → подавлено.
Стиль — как в существующих `test_track`/`test_vote`/`test_pipeline_flow`
(синтетические кадры, стаб-компоненты).

**Живьём (реальная механика)**: телефон IP Webcam → URL в панель → наводишь на
номер → одно событие на показ → в бэк → сессия. Флип направления на Выезд →
закрытие сессии/шлагбаум. **Встроенный демо-источник** (синтетический ролик)
позволяет проверить панель и весь путь **до** подключения телефона.
